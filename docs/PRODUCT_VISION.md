# MAQSAT — Life OS
## Product blueprint · v0.1 · 7 ноября 2026

**Статус:** первая согласованная концепция + кликабельный демонстрационный HTML-макет. **Не production-ready**.

## 1. Видение

MAQSAT — персональная система управления жизнью, доступная в браузере и на телефоне. Смысл продукта — не максимальная статистика и не обязательное выполнение всех дел, а ясность: что важно, какой следующий шаг, как продвигаются проекты и цели и где требуется внимание.

**Основной принцип:** один факт в системе, несколько полезных представлений. Например, задача с назначенным временем появляется в календаре, но не становится вторым независимым объектом.

**Базовая архитектура доступа:** несколько аккаунтов, данные личные по умолчанию. Администратор управляет техническими аккаунтами и приглашениями, но не может читать личные финансы, заметки или здоровье пользователей только из-за роли администратора. Совместные пространства — отдельная опциональная функция второй версии.

## 2. Структура и сценарии

### Постоянная навигация

1. **Главная:** дашборд, фокус дня, ближайшие события, задачи, прогресс целей, краткие финансовые показатели, быстрый ввод.
2. **Планирование:** календарь (день / неделя / месяц), расписание, повторяющиеся события, планирование времени под задачи.
3. **Задачи:** Inbox, списки, статусы, приоритеты, подзадачи, сроки, повторения, связь с проектом и целью.
4. **Корзина идей:** неструктурированный сбор идей; одним действием можно сделать задачу, проект или цель.
5. **Focus Mode:** таймер, выбор задачи/проекта, пауза, история реальных интервалов работы.
6. **Работа:** рабочие проекты, клиенты, учёт времени, договорённые ставки, отчёт по *ожидаемому* заработку.
7. **Финансы:** счета, доходы/расходы, переводы, бюджет, регулярные платежи, категории, история.
8. **Цели:** долгосрочные и краткосрочные, этапы, измерение прогресса, Life Map, связи с задачами/финансами.
9. **Здоровье:** тренировки, упражнения, подходы, журнал питания и необязательная энергетическая ценность, сон и восстановление.
10. **Привычки:** мягкие регулярные напоминания и отметки без наказаний за пропуски.
11. **Аналитика:** агрегированные показатели по задачам, фокусу, работе, финансам и целям.
12. **Настройки:** профиль, язык RU/KZ/EN в перспективе, часовой пояс, безопасность, уведомления, доступность, экспорт/удаление.

### 5 ключевых пользовательских сценариев

**A. Мысль → результат.** Ctrl+K → «Идея» → Inbox → «В задачу» → назначить срок/время → провести Focus Mode → отметить выполненной → прогресс связанной цели пересчитан.

**B. Работа → заработок.** Проект → задачи → трекер времени → сумма за отработанные часы **ожидаемая** → фактический доход отдельно записывается в финансы только при получении оплаты.

**C. Регулярный платёж.** Задать «Мобильная связь / 12 число / каждые 1 месяц» → напоминание → отображение ожидаемого платежа → подтверждение пользователем → фактическая транзакция и изменение баланса.

**D. Спорт.** Шаблон тренировки → событие в календаре → запись подходов → завершение тренировки → аналитика регулярности и изменения результатов. Без требований обязательной прогрессии или соревнования с чужими телесными показателями.

**E. Цели → Life Map.** Цель состоит из этапов, каждый этап связан с одной или несколькими задачами/проектами; для финансовой цели прогресс рассчитывается по выделенным накоплениям; пользователь явно выбирает метод расчёта, чтобы исключить противоречащие проценты.

## 3. Правила бизнес-логики

| Ситуация | Правило |
|---|---|
| Задача и календарь | `due_at` означает дедлайн, `scheduled_start/end` — планируемый блок времени. Это разные поля. |
| Повторяющийся урок | Хранится правило повторения и исключения; перенос одного урока не сдвигает всю серию. |
| Выполнение задачи | Сервер фиксирует состояние, время, владельца и версию; повторная отправка не создаёт две записи. |
| Обновление цели | Прогресс пересчитывается только из выбранных источников или явно устанавливается вручную. |
| Расходы и переводы | Все суммы — decimal, не float; переводы между счетами не считаются доходом/расходом. |
| Регулярные платежи | Планируемый платёж не меняет фактический баланс до подтверждения. |
| Работа и деньги | Прогноз заработка не равен полученному доходу; отметка отработанного времени сама по себе не создаёт поступление. |
| Питание | Добровольный журнал; энергетическая ценность приблизительная, без обязательных лимитов и сравнений пользователей. |
| Аналитика | Строится на записях и их правах доступа; пользователь видит только свои данные. |
| Удаление | Для важных записей — подтверждение, мягкое удаление при необходимости и возможность отмены; отдельный сценарий окончательного удаления аккаунта. |
| Часовой пояс | В хранилище timestamps с tz в UTC; в UI отображать согласно часовому поясу пользователя. По умолчанию Asia/Almaty. |

## 4. UX и дизайн

**Визуальный стиль:** премиальный тёмный и светлый интерфейс, насыщенный фиолетовый акцент (`#9873FB`), мятный для позитивных действий, умеренные бордеры, скругления 12–17 px, типографическая иерархия, спокойные карточки и большое количество воздуха.

**Главная страница:** верхняя панель с быстрым вводом, короткая приветственная строка, 4 KPI, задачи дня, расписание, главные цели, финансовая сводка, корзина идей, переход в Focus Mode. На мобильном — стек карточек и выдвижная навигация.

**Микроинтеракции:** 150–250 ms на обычные переходы, деликатная анимация чекбокса, конфетти только на значимых завершениях, подтверждающие toast-уведомления, мгновенный отклик. Анимации отключаются с `prefers-reduced-motion`.

**Качество взаимодействия:** навигация с клавиатуры, видимые фокусные состояния, достаточный контраст, понятные ошибки, подтверждение разрушительных действий, скелетоны на загрузке, оптимистические обновления только с откатом при ошибке API. Никакого ощущения, что задача «выполнена», если сервер отклонил запрос.

**Быстрое добавление:** Ctrl+K открывает глобальную командную панель. В первом прототипе — упрощённая форма для задачи; в production — команды поиска и создания любого типа записи.

## 5. Предлагаемый production-стек

```text
Browser / PWA
   |
   +-- Frontend: React + TypeScript + Vite
   |      Tailwind CSS / Radix UI, Motion, TanStack Query, React Router
   |
   +-- HTTPS / secure session cookie
          |
          +-- Backend API: FastAPI + Pydantic
          |      SQLAlchemy + Alembic migrations
          |      auth, access control, domain services, background job scheduler
          |
          +-- PostgreSQL on Railway (private networking)
                 users / tasks / events / goals / finance / health ...
```

**Почему:** React/TypeScript удобен для насыщенного интерактивного интерфейса, FastAPI подходит для чётких API и сложной серверной логики, PostgreSQL обеспечивает транзакции и связи между модулями. Railway может запускать фронтенд, API и PostgreSQL раздельными сервисами в одном проекте.

**Рекомендуемый подход:** монолитный backend по доменным модулям, не микросервисы. У каждого модуля свои модели, схемы, сервисы, роутеры и тесты. Для первой версии это проще отлаживать и разворачивать.

## 6. Модель данных и схема БД

В файле `MAQSAT_schema_draft.sql` — согласованный **черновик схемы**, не окончательная миграция. Основные сущности:

- `users`, `auth_sessions`, `life_areas` — пользователи и техническая основа.
- `projects`, `tasks`, `task_items`, `ideas` — проекты, задачи, подзадачи, идеи.
- `calendar_events`, `event_exceptions` — календарь и исключения из повторений.
- `goals` — цели; связи с задачами реализованы через поле `goal_id` или в дальнейшем через связующую таблицу.
- `focus_sessions`, `work_time_entries` — время концентрации и рабочий учёт.
- `finance_accounts`, `finance_transactions`, `recurring_payments` — счета, фактические и планируемые платежи.
- `workouts`, `workout_exercises`, `workout_sets` — силовые и другие тренировки.
- `food_entries` — добровольный журнал питания и необязательные пищевые показатели.
- `habits`, `habit_logs`, `audit_events` — повторения и безопасная наблюдаемость.

**Все приватные таблицы имеют `user_id`**; составные FK предотвращают ссылки на чужие проекты/цели/счета. В реальном API все запросы фильтруются по аутентифицированному владельцу, а не по `user_id`, присланному клиентом. Дополнительно можно включить RLS после настройки отдельной роли приложения и транзакционного контекста пользователя.

## 7. Доступ и безопасность

- **Регистрация:** в первом релизе — приглашения или создание аккаунтов администратором; публичная регистрация включается отдельным решением.
- **Пароли:** Argon2id; никогда не хранить plaintext, не логировать пароль.
- **Сессии:** случайные токены; хранить хеш проверочной части токена на сервере; браузерная cookie — `HttpOnly`, `Secure`, `SameSite`, короткий срок с возможностью отзыва. Не хранить токены входа в `localStorage`.
- **Формы:** CSRF-защита для cookie-аутентификации; валидация данных на сервере; лимиты на попытки входа и восстановления; email-подтверждение и восстановление доступа.
- **Доступ:** серверный контроль владельца КАЖДОЙ записи; тесты `User A -> record B = 403/404`; админ не получает автоматического доступа к чужому дневнику, здоровью или финансам.
- **Инфраструктура:** HTTPS, приватная сеть API↔DB, переменные/секреты только в Railway, CORS с конкретными origin, минимальные права DB-роли.
- **Надёжность:** миграции, резервные копии, периодический тест восстановления, структурные логи без чувствительных данных, централизованный трекинг ошибок.
- **Пользовательский контроль:** экспорт JSON/CSV, удаление учётной записи и личных данных, настройка уведомлений, понятное объяснение обработки данных.

Документация: [Railway PostgreSQL](https://docs.railway.com/databases/postgresql), [Railway private network](https://docs.railway.com/networking/private-networking), [Railway restore](https://railway.com/guides/postgres-backups-restores), [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet).

## 10. Приёмочные критерии для первого production-релиза

1. Пользователь A не может прочитать, изменить или удалить задачи, цели, финансы и здоровье пользователя B, даже подменив ID в URL или запросе.
2. Выход или отзыв сессии блокирует последующие запросы; пароли не появляются в API-ответах/логах.
3. Создание расхода и повторный запрос с тем же idempotency key не создаёт две транзакции.
4. Перевод между собственными счетами не искажает общие доходы и расходы.
5. Повторяющиеся платежи не уменьшают баланс до подтверждения.
6. Задача может иметь отдельный дедлайн и отдельный временной блок.
7. Перенос одной даты в повторяющейся серии не изменяет другие даты.
8. Дашборд корректно работает в телефоне шириной 360–390 px без горизонтальной прокрутки.
9. Все действия можно сделать с клавиатуры; режим reduced motion выключает декоративные анимации.
10. Если API вернул ошибку, изменение визуально откатывается; пользователь получает понятное сообщение.
11. Экспорт данных доступен самому пользователю, а операции удаления требуют подтверждения.
12. Есть зафиксированная и успешно выполненная процедура восстановления БД из бэкапа.

## 11. Что работает в HTML-прототипе

Навигация; переключение темы; задачи и анимация отметки; добавление задач, идей, событий, доходов, расходов, целей, проектов; превращение идеи в задачу; Focus Mode таймер; интерактивные подходы и отметки привычек; некоторые фильтры и вкладки; адаптивный дизайн. **Данные существуют только в памяти открытой страницы и исчезают при обновлении.**

**Не работает и не должно имитироваться как готовое:** реальные аккаунты, серверная авторизация, БД, загрузка в Railway, сохранение данных, банковские интеграции, полноценный расчёт аналитики и календарных повторений.
